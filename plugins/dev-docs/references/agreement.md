# 合意フェーズ

新規作成と大きな改稿では、本文を書く前に 4 つの項目を利用者と合意する。種別ごとの決まった構成は、その文書の議論の筋に合わないことがある。書いてから構成を直すより、目次の段階で直す方が安い。

小さな修正とレビューでは、このフェーズを省く。

## 先に構成を合意するとき

### 資料群の一部を置く依頼では、ページ構成から合意する

「このフォルダに〜の資料を置いて」「〜について情報を整理して」のように、題材が既存の資料群やフォルダの一部にあたる依頼では、1 本の文書の 4 項目を示す前に、ページ構成を合意する。1 本の目次だけを合意すると、既存の資料との重複や、横断で見たい情報（対象ごとの一覧・決定・未決事項）の置き場が決まらないまま書き始めることになる。

示すもの:

- 情報の棚卸し: 関係する情報を種類ごとに分け、今どこにあるか（既存の文書・チャット・コード・個人のメモ）を並べる
- ページ構成: 新しく作るページ、既存の資料をリンクで束ねるページ、動かさない資料を、ツリーで示す。各ページに、そのページが答える問いを 1 行添える
- 置き場: 複数の対象を束ねるページ（概要・入口のページ）は、束ねる範囲のフォルダの直下に置く。個別の対象のフォルダの中に置くと、ほかの対象を探しに来た人がたどり着けない

構成の合意が取れたら、ページごとに下の 4 項目を示す。

### 同種の既存文書とテンプレートを先に探す

書き始める前に、置き場（プロジェクトのフォルダ・スペース・リポジトリ）に同じ種別の既存文書と、会社やチームのテンプレートがあるかを探す。あれば、その構成と文書の呼び名（「PRD」ではなく「要求仕様書」など）にそろえ、合意フェーズの目次でそのことを示す。見つからず、置き場が組織の文書の場所なら、目次を示すときに「テンプレートや手本にしたい既存の文書はあるか」を 1 問聞く。利用者から渡されたテンプレートは、`${CLAUDE_PLUGIN_ROOT}/references/local-rules.md` の `templates/<id>.md` に登録することを提案する。

## 示すもの

次の 4 項目を、1 つのメッセージにまとめて示す。利用者が直しやすいように、項目ごとに短く書く。

### 読者と目的

- 誰が読むか（役割で書く。「判断する開発責任者」「実装を引き継ぐエンジニア」）
- その人がこの文書で何を決める、または何をするか
- 読者が既に知っていること（本文に書かず、付録に送るか省く）

### 答える問い

この文書が答える問いを 1 文で書く（「ログ基盤を 3 案からどれにするか」）。

### 目次

最初に見出しの型（ラベル型かメッセージ型か）を、選んだ理由とあわせて 1 行で示す。既定はラベル型で、読者が通読して判断する文書だけメッセージ型にする（`${CLAUDE_PLUGIN_ROOT}/references/writing.md` の「見出しの型は読者の読み方で選ぶ」）。見出しは本文にそのまま使う文言で書き、各見出しに、その節で言うことを 1 行ずつ添える。階層は字下げで示す。

ラベル型の例（読者が目当ての節を探す DesignDoc）:

```markdown
見出しの型: ラベル型（実装する人が、担当する節を探して読むため）

- 背景と課題 — 今の同期処理は 1 万件でタイムアウトする、を最初の 1 文で言う
- 方針 — 集計を事前計算に寄せる
  - 集計ジョブ — 新しく足す唯一のコンポーネントの責務
- 検討した代替案 — リアルタイム集計を採らない理由
- 未決事項 — 判断者つきの論点
```

メッセージ型の例（開発責任者が通読して 3 案から選ぶ検討資料）:

```markdown
見出しの型: メッセージ型（読者が上から読んで案を選ぶため）

- 推奨は案 B。移行費用が最も小さい — 3 案の比較の結論と、受け入れるトレードオフ
  - 案 B は既存のジョブ基盤をそのまま使える — 追加の運用が要らない根拠
  - 案 A は性能で勝るが移行に 3 か月かかる — 却下の理由
- 判断に要る前提は 2 つ — 期限と許容コスト
- 未決事項 — 判断者つきの論点
```

目次は、種別の reference にある「たたき台の目次」から始めてよい。ただし並び順は、この文書の問いと読者に合わせて組み替える。会社テンプレートがあるときは、テンプレートの見出しをそのまま使い、その下に置く小見出しにだけ選んだ型を当てる。

確かめること:

- ラベル型なら、読者が目当ての節を見出しだけで探せるか。結論は冒頭の要約に置いたか
- メッセージ型なら、見出しだけを上から読んで、問いへの答えまで論旨がたどれるか。最初の見出しに結論があるか
- 後ろの節を読まないと前の節が分からない並びになっていないか

### 用語

本文で使う主要な語を、出所つきで並べる。

```markdown
- 配信ジョブ: 溜まった通知をまとめて送る定期処理（出所: コード）
- 送信上限: 1 時間あたりに送れる通知の件数（出所: 上流文書）
- 再送窓: 失敗した通知を送り直す期間（新規提案）
```

出所は「用語集」「上流文書」「コード」「発話」「新規提案」のどれか。「新規提案」の語は、合意が取れるまで本文に使わない。

## 合意の取り方

- 利用者が直した点を反映し、変わった項目だけを示し直す。全項目を毎回出し直さない
- 「これで書いて」「OK」などの了承を得てから本文に進む
- 利用者が「任せる」と言ったら、示した内容で書き始める
- 合意フェーズで受けた指摘も、`${CLAUDE_PLUGIN_ROOT}/references/learning.md` に従って取り込む
